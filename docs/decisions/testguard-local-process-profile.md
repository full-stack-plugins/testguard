# Linux local lifecycle fixture profile

`testguard-local-lifecycle --local-fixture-v1 JSON` is an explicitly invoked standalone helper for `testguard.lifecycle/linux-fixture-v1`. Its strict configuration accepts only a fixed fixture enum (pass, fail, tree, flood, cleanup_denied, cleanup_stalled), timeout10–10000ms, cleanup10–2000ms and128–65536 output bytes **per pipe**. No executable, shell, argv, environment or working-directory field is accepted. Child executable and arguments are fixed internally; the environment is cleared and stdin detached. `cargo run` still selects the original TestGuard CLI, whose `run` remains unavailable.

The helper alone installs SIGINT/SIGTERM handlers and becomes a Linux subreaper. It starts its fixture in a separate process group. Timeout, control-pipe data, control EOF, signals and stdout/stderr overflow trigger SIGKILL to that group and nonblocking wait of all owned children, including adopted grandchildren. Parent death closes the control pipe if its owner did not duplicate the handle. The fixed fixture never escapes its process group. No `/proc/.../children` kernel feature is required. Reaping and pipe EOF must finish within the cleanup budget; polling has normal OS scheduling latency. No portable hard realtime guarantee is claimed.

Each output reader retains at most the configured byte prefix and drains/discards excess until termination. Overflow, reader errors, signal death and cleanup failure never produce `Completed`. Report exit codes are present only for completed native exits; `Completed` plus exit1 remains a failed execution, not a passing test. Interrupted/unobserved cases remain unknown; these diagnostic reports issue no GuardEngine envelope or eligibility. Already captured bytes, including earlier failure diagnostics, survive rejected/partial runs. They are raw diagnostics, not authenticated artifacts or trustworthy native test results. Existing rooted artifact collectors remain the collection boundary.

`cleanup_denied` and `cleanup_stalled` are explicit fault fixtures: a private kill seam respectively returns EPERM or performs an ineffective kill against an actual running tree. The latter exercises real cleanup-deadline expiry. A further100ms best-effort real kill/wait rescue prevents fixture leaks. The report preserves `CleanupFailed`, null exit and `cleanup_complete=false` even if rescue succeeds. These are injected failures, not claims of observed OS permission denial. Successful normal cleanup has no extra rescue window.

This is not an OS sandbox, network/filesystem isolation, arbitrary malicious-process supervisor, production executor, native Cargo/Maven runner or approval authority. Workspace tests prove the fixed fixtures write no files; they do not establish access isolation. Descendants that create a new process group are unsupported. Killing the supervisor with SIGKILL can prevent cleanup and all output; absence of a report must never imply success. Non-Linux invocation returns unsupported/4. The library helper entry is only for the dedicated executable; a host application must launch the helper, never call it in-process and change its own signal/reaping state.

Verification: real child and grandchild PIDs disappear from `/proc` after timeout, repeated cancellation, control EOF and SIGINT/SIGTERM; simultaneous stdout/stderr floods are bounded; original nonzero exit survives; injected denied/over-budget cleanup stays incomplete; strict profile/budget rejection emits no completion report. Each run uses an empty temporary cwd and verifies no files appeared.
